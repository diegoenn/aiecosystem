Git & GitHub — Guía de referencia diaria

Del primer git init a un Pull Request aprobado en main, con las prácticas de seguridad que sigo en el día a día.

Fundamentos Git GitHub VS Code

En esta guía

  1. Crear un nuevo repositorio en GitHub

1Crear un nuevo repositorio en GitHub

Opción A — Desde GitHub.com (repo remoto primero)

  1. Entra a github.com → botón New repository.
  2. Define nombre, visibilidad (Public/Private) y marca Add a README.
  3. Agrega un .gitignore según el lenguaje (Node, Python, etc.) — evita subir node_modules, .env, archivos de build.
  4. Clona el repo a tu máquina (ver sección 2).

Opción B — Desde un proyecto local ya existente

git init
git add .
git commit -m "chore: initial commit"
git branch -M main
git remote add origin https://github.com/usuario/nombre-repo.git
git push -u origin main
✅
Buenas prácticas
  • Usa main como nombre de rama principal (estándar actual, reemplaza a master).
  • Crea el .gitignore antes del primer commit para no subir archivos sensibles.
  • Nunca subas credenciales, .env, tokens o llaves — usa variables de entorno o GitHub Secrets.

2Clonar un repositorio de forma segura desde VS Code

Recomendado: autenticación SSH (más segura que HTTPS con contraseña).

1. Genera una llave SSH si no tienes una

ssh-keygen -t ed25519 -C "tu_email@ejemplo.com"

2. Copia la llave pública y agrégala en GitHub

GitHub → Settings → SSH and GPG keys → New SSH key.

cat ~/.ssh/id_ed25519.pub

3. Verifica la conexión

ssh -T git@github.com

Clonar desde VS Code

  1. Ctrl/Cmd + Shift + P → Git: Clone.
  2. Pega la URL en formato SSH: git@github.com:usuario/repo.git.
  3. Elige la carpeta local destino.
  4. VS Code te pregunta si quieres abrir el repo → Open.
✅
Buenas prácticas
  • Usa SSH en vez de HTTPS + contraseña (evita reautenticarte y es más seguro).
  • Si usas HTTPS, autentícate con un token de acceso personal (PAT), nunca con tu contraseña de cuenta (GitHub ya no lo permite).
  • Revisa siempre la URL del repo antes de clonar (evita repos maliciosos con nombres parecidos — typosquatting).
  • Activa 2FA en tu cuenta de GitHub.

3Hacer un commit seguro desde VS Code

Flujo recomendado

  1. Panel Source Control (Ctrl/Cmd + Shift + G).
  2. Revisa el diff de cada archivo modificado antes de hacer stage (clic en el archivo).
  3. Haz stage solo de los archivos relevantes al cambio (no "stage all" a ciegas).
  4. Escribe un mensaje de commit siguiendo Conventional Commits:
feat: agrega validación de CPT code en scheduler
fix: corrige timeout en llamada a Okta SSO
docs: actualiza README con pasos de instalación
refactor: simplifica lógica de routing de citas
  1. Commit → Ctrl/Cmd + Enter o el botón ✔.

Desde terminal (equivalente)

git status
git diff
git add archivo1.js archivo2.js
git commit -m "feat: descripción clara del cambio"
✅
Buenas prácticas
  • Nunca hagas git add . sin revisar antes qué se incluye (riesgo de subir .env, logs, credenciales).
  • Commits pequeños y atómicos (un propósito por commit) — facilita revertir si algo falla.
  • Mensajes descriptivos, no "fix" o "cambios".
  • Antes de hacer push, trae los cambios del remoto:
git pull --rebase origin main
  • Instala la extensión GitLens en VS Code para ver historial y autoría línea por línea.

4Tipos de ramas en GitHub

Tipo de ramaPropósitoEjemplo
main / masterCódigo en producción, siempre estable y desplegablemain
develop (opcional, según flujo)Integración de features antes de pasar a produccióndevelop
feature/*Desarrollo de una funcionalidad nuevafeature/ai-scheduler-cpt-routing
bugfix/*Corrección de errores no urgentesbugfix/okta-token-expiry
hotfix/*Corrección urgente directo sobre producciónhotfix/login-crash
release/*Preparación de una versión antes de publicarlarelease/v2.3.0

Este esquema se conoce como Git Flow. Para equipos ágiles con despliegues frecuentes, muchos usan Trunk-Based Development (ramas feature/* cortas que se integran a main varias veces por semana, apoyadas en feature flags como LaunchDarkly).

5Cómo manejar las ramas mientras editas código

Flujo estándar por tarea/feature

# 1. Parte siempre de main actualizado
git checkout main
git pull origin main

# 2. Crea tu rama de trabajo
git checkout -b feature/nombre-descriptivo

# 3. Trabaja, haz commits pequeños
git add .
git commit -m "feat: ..."

# 4. Mantén tu rama sincronizada con main (evita conflictos grandes al final)
git checkout main
git pull origin main
git checkout feature/nombre-descriptivo
git rebase main   # o: git merge main

# 5. Sube tu rama
git push -u origin feature/nombre-descriptivo

Desde VS Code: la barra inferior izquierda muestra la rama activa → clic para crear/cambiar rama (Create new branch). El ícono de sincronización (⟳) hace pull + push en un clic.

✅
Buenas prácticas
  • Una rama = una tarea/feature/bug. No mezcles cambios de temas distintos.
  • Nombres descriptivos: feature/, bugfix/, hotfix/ + ticket/descripción (feature/JIRA-123-sso-timeout).
  • Sincroniza seguido con main para evitar conflictos gigantes al final.
  • Borra la rama local y remota después de mergear:
git branch -d feature/nombre-descriptivo
git push origin --delete feature/nombre-descriptivo

6Cuándo y cómo publicar código a main/master

Cuándo

  • Cuando la funcionalidad está completa, probada y revisada (no antes).
  • Nunca hagas push directo a main en equipo — siempre vía Pull Request (PR).
  • Idealmente main debe tener protección de rama activada (branch protection rules) que exija PR + al menos 1 revisor + checks de CI en verde.

Cómo (flujo con Pull Request)

  1. Sube tu rama: 
    git push -u origin feature/nombre-descriptivo
  2. En GitHub → Compare & pull request.
  3. Describe el cambio: qué hace, cómo probarlo, tickets relacionados.
  4. Espera revisión de un compañero y que pasen los checks de CI/CD (GitHub Actions, tests, Playwright).
  5. Resuelve comentarios con commits adicionales o git commit --amend si aplica.
  6. Una vez aprobado: Merge pull request (preferible Squash and merge para mantener historial limpio en main).
  7. Borra la rama feature (GitHub lo ofrece automáticamente al mergear).

Configuración recomendada en GitHub (Settings → Branches)

  • ✅ Require pull request before merging.
  • ✅ Require approvals (mínimo 1).
  • ✅ Require status checks to pass (CI/CD, tests).
  • ✅ Require branches to be up to date before merging.
  • 🚫 No permitir force push a main.
✅
Buenas prácticas
  • Nunca publiques directo a main sin PR, aunque el cambio parezca pequeño.
  • Usa release notes / tags para versiones importantes:
git tag -a v1.2.0 -m "Release v1.2.0"
git push origin v1.2.0
  • Si algo falla en producción, usa una rama hotfix/* desde main, corrige, y mergea con PR expedito.

7Resumen de comandos más usados en el día a día

git status                       # ver estado actual
git pull origin main             # traer cambios del remoto
git checkout -b feature/x        # crear y moverte a nueva rama
git add <archivo>                # stage de cambios específicos
git commit -m "tipo: mensaje"    # commit con mensaje claro
git push -u origin feature/x     # subir rama por primera vez
git log --oneline --graph        # ver historial visual
git diff                         # ver cambios no confirmados
git stash                        # guardar cambios sin commitear temporalmente
git rebase main                  # actualizar tu rama con main
